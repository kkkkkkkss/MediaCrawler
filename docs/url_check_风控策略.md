# url_check 模式风控与优化策略

## 反检测措施

### 1. CDP 模式（推荐）
- 使用用户本地 Chrome 浏览器，具有完整的浏览器指纹
- 复用用户已有的 Cookie、扩展、浏览历史
- 通过 `CDP_CONNECT_EXISTING = True` 连接已打开的浏览器，反检测效果最佳
- 相关配置：`config/base_config.py` 中 `ENABLE_CDP_MODE` 和 `CDP_CONNECT_EXISTING`

### 2. 请求节流
- `CRAWLER_MAX_SLEEP_SEC = 2`：每个 URL 处理后等待 2 秒
- 建议在网络环境较敏感时适当增大此值（如 3-5 秒）
- url_check 模式采用串行处理，不会并发请求同一平台

### 3. 平台隔离
- 每个平台独立启动浏览器会话，互不干扰
- 处理完一个平台后关闭浏览器再启动下一个
- 避免了跨平台 Cookie 污染

## 并发策略

### 当前设计：串行处理
- 每次只处理一个平台的 URL
- 同一平台内逐个 URL 串行处理
- 优点：风险最低，不易触发风控
- 缺点：速度较慢

### 批量控制
- `URLCHECK_BATCH_SIZE` 控制每次从数据库读取的 URL 数量
- 建议初期设置为 10-20，稳定后逐步增大到 50-100
- 每批处理完后可重新运行以处理新增的 URL

## AI 成本控制

### Token 消耗
- 每次 AI 调用约消耗 500-2000 tokens（取决于 JSON 大小）
- 输入 JSON 截断到 8000 字符，防止 token 爆炸
- 日志中会记录每次调用的 token 消耗和累计统计

### 回退机制
- AI 调用超时（30秒）或失败时，自动回退到硬编码映射
- 硬编码映射不消耗 AI token，速度更快
- 两层机制确保即使 AI 服务不可用也能正常运行

### 成本优化建议
- 如果某平台的 JSON 结构稳定，可以在 `fallback_field_map.py` 中完善映射后关闭该平台的 AI 调用
- 运行日志中关注 `[AIFieldMapper]` 前缀的信息以监控 AI 使用情况

## 数据安全

### 密钥管理
- 所有敏感信息（数据库密码、API Key、Cookie）仅通过 `.env` 注入
- `.env` 已在 `.gitignore` 中，不会提交到代码仓库
- 代码中不包含任何硬编码的密钥或密码

### 数据库安全
- 外部业务库连接（ExternalDB）与 MediaCrawler 自身库完全隔离
- 使用参数化查询，防止 SQL 注入
- 连接池最大连接数限制为 5，避免压垮数据库

### 去重安全
- 评论写入使用 `ON DUPLICATE KEY UPDATE`，支持重跑不会产生重复数据
- 指标更新按 `id` 精确更新，不会影响其他行

## 常见风控场景与应对

| 场景 | 表现 | 应对方式 |
|------|------|----------|
| IP 被封 | 请求超时或返回空 | 启用代理 IP（`ENABLE_IP_PROXY = True`） |
| 登录态失效 | 接口返回未登录 | 重新扫码登录或更新 Cookie |
| 滑动验证码 | 浏览器弹出验证 | 设 `HEADLESS = False` 手动通过 |
| 请求频率限制 | 接口返回错误码 | 增大 `CRAWLER_MAX_SLEEP_SEC` |
| 头条页面结构变化 | SSR 数据提取失败 | 更新 `ToutiaoClient` 中的 JS 提取逻辑 |

## 扩容建议

当 URL 量增长到万级别时：

1. **分批运行**：通过调大 `URLCHECK_BATCH_SIZE` 并多次运行
2. **增加间隔**：`CRAWLER_MAX_SLEEP_SEC` 建议设为 3-5 秒
3. **代理 IP**：启用 IP 代理池以降低单 IP 被封风险
4. **定时调度**：用 cron 或任务调度器定时执行，避免集中大量请求
5. **监控告警**：关注日志中 `is_valid=2` 的比例，如果突然升高可能是风控触发
