# 同平台多浏览器并发 - 原理与逻辑说明

## 设计动机

### 原有架构的瓶颈

改造前，同一平台内只有 1 个浏览器串行处理所有 URL：

```
平台 toutiao: [URL1] → [URL2] → [URL3] → ... → [URL10]
              每条约 5~7 秒 (goto + sleep + DOM提取)
              总耗时 ≈ 10 × 6 = 60 秒
```

对于头条这种不需要登录的平台，浏览器之间完全独立，多开不增加风控。
对于需要登录的平台，只要每个浏览器用不同的 Cookie，单账号请求频率不变。

### 改造后

```
平台 toutiao (3个浏览器并发):
  Worker1: [URL1] → [URL4] → [URL7] → [URL10]
  Worker2: [URL2] → [URL5] → [URL8]
  Worker3: [URL3] → [URL6] → [URL9]
  总耗时 ≈ 4 × 6 = 24 秒 (取决于最慢的Worker)
```

加速比 ≈ 并发数。

## 整体架构

```
_process_platform(platform, url_rows, mode)
  │
  ├─ HTTP 预检（不变，快速过滤失效URL）
  │
  ├─ _resolve_concurrency(platform, url_count)
  │   ├─ cookie_free 平台 → min(配置值, URL数)
  │   └─ 需Cookie平台 → min(配置值, 可用Cookie数, URL数)
  │
  ├─ concurrency == 1 → _process_platform_single（原有逻辑）
  │
  └─ concurrency > 1 → _process_platform_concurrent
       │
       ├─ 分配Cookie：allocate_cookies(platform, concurrency)
       │   ├─ cookie_free → [None, None, None]
       │   └─ 需Cookie → [(id1,str1), (id2,str2), ...]
       │
       ├─ 创建共享 asyncio.Queue → 放入所有 URL
       │
       └─ asyncio.gather(
            _browser_worker(W1, cookie1, queue),
            _browser_worker(W2, cookie2, queue),
            _browser_worker(W3, cookie3, queue),
          )
```

## 核心组件

### 1. `_resolve_concurrency` — 并发数计算

```python
def _resolve_concurrency(self, platform, url_count):
    configured = PLATFORM_CONCURRENCY.get(platform, 1)
    
    if platform in COOKIE_FREE_PLATFORMS:
        return min(configured, url_count)
    else:
        available_cookies = cookie_pool.get_valid_count(platform)
        return min(configured, available_cookies, url_count)
```

关键逻辑：
- 不会开超过 URL 数量的浏览器（3条URL只开3个浏览器，不开5个）
- 不会开超过可用 Cookie 数的浏览器（只有2个Cookie就只开2个）
- 最少为1

### 2. `_browser_worker` — 单浏览器工作协程

每个 Worker 独立运行，拥有独立的：
- Playwright 进程
- 浏览器上下文（browser_context）
- 页面（context_page）
- Cookie

工作循环：
```
while queue不为空 and 未达到软上限:
    row = queue.get_nowait()
    process_single_url(row)
    
    if Cookie失效:
        new_cookie = get_unused_cookie(exclude=已用IDs)
        if new_cookie:
            重建Client继续
        else:
            break
    
    sleep(PLATFORM_SLEEP_SEC)
```

### 3. `_create_worker_client` — 为Worker创建浏览器

两种模式：
- **cookie_free**：直接启动浏览器，导航到首页，不注入Cookie
- **有Cookie**：启动浏览器 → 注入Cookie → 导航到首页 → 创建Client

### 4. `_try_rebind_cookie` — Cookie 失效重绑定

当检测到 Cookie 失效（`_fetch_fail_reason == auth_failed`）时：
1. 向 cookie_pool 报告 FATAL 失败
2. 调用 `get_unused_cookie(exclude=所有已用IDs)` 获取新 Cookie
3. 关闭旧浏览器，创建新浏览器和 Client
4. 更新 `used_cookie_ids` 集合

### 5. 共享队列 (asyncio.Queue)

所有 Worker 从同一个 Queue 中取 URL：
- 天然负载均衡：处理快的 Worker 多取，慢的少取
- 某 Worker 停止后，队列中的剩余 URL 由其他 Worker 自动消费
- 无需预先分配，避免不均匀问题

## 与跨平台并行的关系

两层并发协同工作：

```
第一层：跨平台并行 (asyncio.gather)
  ├─ 平台 dy → _process_platform → concurrency=2 → 2个Worker
  ├─ 平台 bili → _process_platform → concurrency=1 → 单浏览器
  ├─ 平台 toutiao → _process_platform → concurrency=3 → 3个Worker
  └─ ...

总浏览器数 = sum(每个平台的实际并发数)
```

---

## 软上限机制

`MAX_URLS_PER_COOKIE` 控制单个浏览器/Cookie 处理的最大 URL 数：

```
场景：200条URL, 3个Cookie, MAX_URLS_PER_COOKIE=50

Worker1: 处理50条 → 达到上限 → 停止取新URL
Worker2: 处理50条 → 达到上限 → 停止取新URL
Worker3: 处理50条 → 达到上限 → 停止取新URL
队列中剩余50条 → 被标记为"未处理"（Cookie全部达到上限）

解决方案：增大 MAX_URLS_PER_COOKIE 或增加 Cookie 数量
设为 0 则不限制，自然均分
```

## 风控安全分析

| 维度 | 单浏览器模式 | 多浏览器并发模式 | 风险变化 |
|------|------------|--------------|---------|
| 单账号请求频率 | 1条/N秒 | 1条/N秒 | 不变 |
| 单IP请求频率 | 1条/N秒 | M条/N秒 | 增加(M=并发数) |
| 单平台总请求量 | 不变 | 不变 | 不变 |
| 浏览器指纹 | 1个 | M个不同 | 更分散 |

**结论**：
- 对账号级风控无影响（每账号频率不变）
- 对 IP 级风控有轻微影响（多浏览器共用IP时频率增加）
- 建议高并发时配合动态IP/隧道代理

---

## 兼容性保证

- `concurrency == 1` 时完全走原有单浏览器逻辑，无额外开销
- 旧配置无 `PLATFORM_CONCURRENCY` 时默认全部为1，行为不变
- Cookie 池为空时自动回退单浏览器模式
