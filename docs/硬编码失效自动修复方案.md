# 硬编码字段映射失效 — 自动修复方案对比

## 背景

当前采集链路：
1. **硬编码映射**优先：从 API 返回的 JSON 中，按预定义路径提取「点赞、评论、播放量」
2. **AI 补充提取**兜底：当硬编码提取结果全为 0/null 时，调用豆包 AI 对完整 JSON 做二次提取

### 核心风险

平台一旦调整接口字段（如 `digg_count` → `like_count`），硬编码映射整体失效。此时**每一条 URL 都会走 AI 提取**：
- 以 3000 token/条估算，1000 条采集即消耗 3M tokens
- 按豆包 Pro 模型定价，单次批量成本可能突破预算

---

## 方案 A：AI 提取后自动通知开发者

### 流程

```
硬编码失效 → AI 提取兜底
         ↓
   AI 分析错误原因
   (对比原 JSON 和预期字段路径)
         ↓
   生成「修复建议报告」
   (明确哪些字段路径变了、新路径是什么)
         ↓
   通知开发者（钉钉/邮件/企微）
         ↓
   开发者手动修复 + 测试 + 上线
```

### 落实步骤

1. **失效检测模块**：在 `ai_field_mapper.py` 中，当连续 N 条（如 3 条）都触发了 AI 兜底时，触发告警
2. **错误分析 Prompt**：让 AI 比较原始 JSON 结构和 `fallback_field_map.py` 中的字段路径，输出差异报告
3. **通知集成**：接入钉钉 Webhook / 企微 Bot / 邮件 SMTP，发送包含修复建议的告警消息
4. **限流保护**：触发告警后，自动切换为 `hardcode_only` 模式（不再调用 AI），避免成本失控

### 优点

- **实现简单**：仅需添加计数器 + 告警通知，代码改动量小（约 100 行）
- **安全可控**：人工审核修复方案后再上线，不存在自动修改引入 bug 的风险
- **成本低**：通知本身零成本，触发后立即止损

### 缺点

- **响应慢**：依赖开发者在线时间，夜间/节假日可能数小时无人处理
- **中间损失**：从发现到修复上线期间，要么不采集，要么持续消耗 AI token
- **重复劳动**：每次字段变更都需要人工介入

---

## 方案 B：通过 AgentHub 自动修复代码

### 流程

```
硬编码失效 → AI 提取兜底
         ↓
   连续失效触发自动修复
         ↓
   调用 AgentHub API
   (传入：原始 JSON 样本 + 当前 fallback_field_map.py 代码)
         ↓
   AgentHub Agent 分析并修改代码
         ↓
   Agent 执行自动化测试
   (用最近的 5 条 URL 验证修复后的硬编码能否正确提取)
         ↓
   测试通过 → 提交 PR + 通知开发者审批上线
   测试失败 → 回退 + 告警通知（降级为方案A）
```

### 落实步骤

1. **触发条件**：与方案 A 相同的连续失效检测
2. **AgentHub 调用封装**：
   - 编写一个 `auto_fix_hardcode.py` 模块
   - 构造 Prompt：包含原始 JSON 样本（脱敏）、当前字段映射代码、期望输出格式
   - 调用 AgentHub HTTP API，传递 Skill 和代码仓库路径
3. **测试验证环节**：
   - Agent 修改 `fallback_field_map.py` 后，在 worktree 中运行：`pytest tests/test_field_map.py`
   - 或直接用最近采集的 5 条真实 JSON 做断言验证
4. **PR + 通知**：
   - Agent 测试通过后创建 Git branch → commit → push → 创建 PR
   - 通知开发者："字段映射已自动修复，请审批 PR #xxx"
5. **降级策略**：Agent 修复失败或测试不通过时，自动降级为方案 A（通知人工修复）

### 优点

- **响应快**：从检测到修复 PR 可在 5-10 分钟内完成
- **全天候**：无需等待人工在线
- **规模化**：多平台同时失效时可并行修复

### 缺点

- **实现复杂**：需要对接 AgentHub API、编写 Skill、搭建测试用例
- **修复质量风险**：Agent 可能生成不完美的代码（需要 PR 人工审批保底）
- **基础设施依赖**：AgentHub 平台的可用性直接影响修复能力
- **初始投入大**：预计需要 3-5 天完成 Skill 编写和联调

---

## 推荐方案

**推荐「方案 A + B 组合」：先实现 A 保底，再逐步接入 B 增强**

### 理由

1. 方案 A 实现成本极低（半天即可完成），能立即解决成本失控问题
2. 方案 B 作为增强，在 A 的基础上逐步完善，而不是从零开始
3. B 的降级策略本身就是 A，形成完整的容错链路

### 建议实施路径

| 阶段 | 内容 | 预计工时 |
|------|------|---------|
| 第一阶段 | 实现方案 A（检测+止损+通知） | 0.5-1 天 |
| 第二阶段 | 编写 AgentHub Skill + 测试用例 | 2-3 天 |
| 第三阶段 | 联调 Agent 自动修复 + PR 流程 | 1-2 天 |
| 第四阶段 | 生产环境验证 + 调优 | 持续 |

### 关键代码变更点

```
tools/ai_field_mapper.py     → 添加连续失效计数器 + 触发逻辑
tools/auto_fix_hardcode.py   → 新增：AgentHub 调用封装
tools/fallback_field_map.py  → 被 Agent 自动修改的目标文件
config/base_config.py        → 添加 ALERT_WEBHOOK_URL、AGENTHUB_API_KEY 等配置
tests/test_field_map.py      → 新增：字段映射自动化测试
```
