# 多平台并行爬取 - 原理与逻辑说明

## 设计思路

### 问题分析

原有架构按平台**顺序**处理：

```
抖音(3条) → B站(2条) → 快手(1条) → 微博(2条) → 头条(1条)
     串行执行，总耗时 = 各平台耗时之和
```

由于风控限制，每个平台同一时间只能爬取一条链接，所以**平台内**无法并行。但**跨平台**之间是完全独立的：不同平台使用不同的账号、不同的Cookie、不同的浏览器上下文。

### 核心洞察

> 对于每个平台的风控系统来说，它只能观察到来自自己平台的请求频率。
> 5个平台各开一个浏览器，每个浏览器一次处理一条链接，对每个平台来说等价于只有一个用户在正常浏览。

因此可以安全地并行处理多个平台。

## 架构设计

### 改造前（顺序模式）

```
UrlCheckCrawler (单实例)
  ├── 处理平台 dy: 打开浏览器 → 逐条处理 → 关闭浏览器
  ├── 处理平台 bili: 打开浏览器 → 逐条处理 → 关闭浏览器
  ├── 处理平台 ks: 打开浏览器 → 逐条处理 → 关闭浏览器
  └── ...
```

### 改造后（并行模式）

```
主调度器
  ├── asyncio.gather(
  │     Worker-dy  (独立 Crawler + 独立浏览器) → 逐条处理 dy 链接,
  │     Worker-bili (独立 Crawler + 独立浏览器) → 逐条处理 bili 链接,
  │     Worker-ks  (独立 Crawler + 独立浏览器) → 逐条处理 ks 链接,
  │     Worker-wb  (独立 Crawler + 独立浏览器) → 逐条处理 wb 链接,
  │     Worker-toutiao (独立 Crawler + 独立浏览器) → 逐条处理 toutiao 链接,
  │   )
  └── 合并所有 Worker 的结果
```

## 代码结构

### 涉及文件

| 文件 | 改动 |
|------|------|
| `config/base_config.py` | 新增 `URLCHECK_PARALLEL_PLATFORMS` 配置 |
| `media_platform/url_check/core.py` | 新增 `_process_platforms_parallel` 方法 |
| `api/service.py` | 新增 `_parallel_platform_process` 和 `_sequential_platform_process` |

### 关键实现

#### 1. 独立实例隔离

每个平台创建独立的 `UrlCheckCrawler` 实例：

```python
async def _platform_worker(platform, url_rows):
    worker = UrlCheckCrawler()  # 独立实例，独立浏览器上下文
    await worker._process_platform(platform, url_rows, mode)
    return worker
```

这确保了：
- 各平台的 `browser_context` 互不干扰
- Cookie 注入隔离，不会串台
- 某平台异常不影响其他平台

#### 2. 并行启动

使用 `asyncio.gather` 并行启动所有平台 Worker：

```python
tasks = [_platform_worker(p) for p in active_platforms]
workers = await asyncio.gather(*tasks, return_exceptions=True)
```

`return_exceptions=True` 保证某个平台失败不会中断其他平台。

#### 3. 进度安全更新

多协程并发更新进度时使用 `asyncio.Lock` 保证数据一致性：

```python
progress_lock = asyncio.Lock()

async with progress_lock:
    info.processed += 1
    info.progress = (info.processed / info.total) * 100
```

#### 4. 结果合并

所有 Worker 完成后，将各自的结果列表合并：

```python
for result in workers:
    if hasattr(result, "_all_results"):
        all_results.extend(result._all_results)
```

## 性能对比

假设5个平台各有3条链接，每条处理耗时约5秒：

| 模式 | 总耗时（理论值） | 说明 |
|------|----------------|------|
| 顺序模式 | 5×3×5 = 75秒 | 逐平台、逐条 |
| 并行模式 | 3×5 = 15秒 | 5个平台同时处理，瓶颈是最多链接的平台 |
| **加速比** | **~5倍** | 等于并行平台数 |

实际加速效果取决于平台数量和各平台 URL 分布均匀程度。

## 风控安全分析

| 维度 | 分析 | 结论 |
|------|------|------|
| 单平台请求频率 | 每个平台内仍逐条顺序处理，间隔 `CRAWLER_MAX_SLEEP_SEC` | 无变化 |
| 单账号并发 | 每个平台的 Cookie 只在一个浏览器中使用 | 无变化 |
| IP层面 | 所有浏览器共用出口 IP，但请求分散到不同域名 | 风险极低 |
| 浏览器指纹 | 每个浏览器独立 context，UserAgent/指纹独立 | 安全 |

**结论**：并行不增加任何单平台的风控压力。

## 回退机制

当以下条件成立时，自动回退为顺序模式：

1. `URLCHECK_PARALLEL_PLATFORMS = False`
2. 当前批次只有1个平台的链接
3. 在 `core.py` 的 CLI 模式下（`start()` 方法），同样遵循此逻辑
