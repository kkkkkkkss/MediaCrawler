# 拟人化反风控 - 原理与逻辑说明

## 设计动机

### 问题背景

多浏览器并发爬取时，同一 IP 地址同时打开多个浏览器窗口，平台风控系统可能检测到以下异常：

1. **瞬时多连接**：同一 IP 在同一秒内建立多条 TCP 连接并打开多个 WebSocket/HTTP2 通道
2. **请求节奏一致**：多个浏览器以完全相同的间隔发起请求（如精确的 2.000 秒）
3. **指纹关联**：多个浏览器窗口尺寸、User-Agent 完全一致，容易被判定为同一程序控制

### 解决思路

通过在时间维度和指纹维度引入随机性，使多个浏览器的行为模式更接近**多个独立用户**，而非一个爬虫程序的多线程。

---

## 三项反风控措施

### 1. 浏览器错峰启动（Staggered Launch）

**原理**：在每个 Worker 启动浏览器前，插入 `[0, BROWSER_STAGGER_MAX_SEC]` 范围内的随机延迟。

```
改造前（同时启动）：
  时间线: ─── 0s ────────────────────────────────
  W1:     [启动浏览器]
  W2:     [启动浏览器]    ← 同一时刻，IP 瞬时 3 个浏览器连接
  W3:     [启动浏览器]

改造后（错峰启动）：
  时间线: ─── 0s ── 0.5s ── 1.2s ─────────────
  W1:     [启动浏览器]
  W2:          [延迟0.5s][启动浏览器]
  W3:               [延迟1.2s][启动浏览器]
```

**关键实现**：
- 第一个 Worker（`worker_id == 1`）不延迟，确保不增加总体启动时间
- 延迟使用 `random.uniform(0, max)` 生成均匀分布的随机值
- 延迟发生在 `async_playwright()` 上下文之前，不占用 Playwright 资源

**代码位置**：`media_platform/url_check/core.py` → `_browser_worker` 方法开头

### 2. 请求间隔抖动（Sleep Jitter）

**原理**：将固定的请求间隔改为带随机偏移的动态间隔。

```
改造前（固定间隔）：
  W1: [URL1]──2s──[URL2]──2s──[URL3]──2s──
  W2: [URL4]──2s──[URL5]──2s──[URL6]──2s──
  ↑ 每个 Worker 的请求间隔完全相同，行为模式机械化

改造后（随机间隔，SLEEP_JITTER_RATIO=0.3）：
  W1: [URL1]──1.8s──[URL2]──2.4s──[URL3]──1.5s──
  W2: [URL4]──2.2s──[URL5]──1.6s──[URL6]──2.5s──
  ↑ 间隔在 [2×0.7, 2×1.3] = [1.4, 2.6] 之间随机
```

**计算公式**：
```
actual_sleep = base_sleep × (1 + random.uniform(-jitter_ratio, jitter_ratio))
```

**效果**：即使两个 Worker 碰巧在同一时刻完成了上一条 URL，下一条请求的发起时间也不会对齐。

**代码位置**：`media_platform/url_check/core.py` → `_browser_worker` 方法末尾的 `asyncio.sleep`

### 3. 视口尺寸随机化（Viewport Randomization）

**原理**：每个 Worker 的浏览器窗口在基础尺寸上随机偏移，使每个浏览器产生不同的浏览器指纹。

```
Worker1: viewport = 1935 × 1062
Worker2: viewport = 1887 × 1104
Worker3: viewport = 1951 × 1041
```

**为什么有效**：
- 浏览器指纹中 `screen.width`、`screen.height`、`innerWidth`、`innerHeight` 是重要特征
- 完全相同的分辨率 + 同一 IP = 高度关联 → 被判定为同一爬虫程序
- 不同的分辨率 = 看起来像是不同的设备

**代码位置**：`media_platform/url_check/core.py` → `_create_worker_client` 方法中的 viewport 参数

## 前端日志增强

### 新增信息

在批量检测的实时日志中，为每条结果添加了 Worker 编号和 Cookie 标识：

```
旧格式：[头条][DOM] 有效 | 赞=15 评=7 ...
新格式：[头条][W2|无Cookie][DOM] 有效 | 赞=15 评=7 ...
         ↑ Worker 编号   ↑ Cookie 标识
```

### 实现方式

1. 在 `_browser_worker` 中，每条 URL 处理前将 `worker_id` 和 `cookie_id` 写入 `row` 字典
2. 处理完成后，`on_result` 回调从 `row` 中读取这些信息并格式化到日志

```
数据流：
_browser_worker → row["_worker_id"] = 2
                  row["_cookie_id"] = "dy_01"
    ↓
_on_result(row) → "[抖音][W2|Cdy_01][硬编码] 有效 | ..."
    ↓
前端 TaskList → 日志面板实时显示
```

## 风控防护效果评估

| 维度 | 无拟人化 | 有拟人化 | 降低风险 |
|------|---------|---------|---------|
| 多浏览器同时连接 | 同一毫秒建立 N 个连接 | 分散在 0~3 秒内逐个连接 | 显著 |
| 请求时间模式 | 精确固定间隔（机器人特征） | 随机波动间隔（人类特征） | 中等 |
| 浏览器指纹关联 | N 个浏览器完全相同指纹 | 每个浏览器不同分辨率 | 中等 |
| 单账号请求频率 | 不变 | 不变 | 无变化 |
| 总吞吐量影响 | - | 略有降低（错峰启动+随机间隔） | 约 3~5% |

## 与其他风控措施的配合

拟人化措施是**客户端行为层**的反风控，应与其他层级配合：

```
┌──────────────────────────────────────────────┐
│  IP 层：动态代理 / 隧道代理（IP 轮换）          │
├──────────────────────────────────────────────┤
│  账号层：Cookie 池（多账号轮换，单账号频率不变） │
├──────────────────────────────────────────────┤
│  行为层：拟人化（错峰启动 + 间隔抖动 + 指纹分散）│ ← 本次新增
├──────────────────────────────────────────────┤
│  业务层：软上限（MAX_URLS_PER_COOKIE 防过量）   │
└──────────────────────────────────────────────┘
```
